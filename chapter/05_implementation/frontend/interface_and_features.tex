\chapter{Design and Implementation of Frontend}

At the start of the project, we focused on understanding the client's requirements in detail to make sure we were clear about the goals and user needs. This gave us a clear picture of both functional and non-functional requirements. Based on this insight, we carefully evaluated and selected the most suitable technologies to implement the Tourlingo application efficiently and sustainably. To visualize the user experience and interface, we designed detailed wireframes and interactive prototypes using Figma, which was helpful to get early feedback and iterative improvements before moving into full development.

\section{Tech Stack Selection and Justification}

With a comprehensive understanding of the client's requirements, our next step was to carefully evaluate and select a technology stack that balances scalability, maintainability, performance, and developer experience. Each layer of the frontend architecture was considered through a comparative analysis of available tools and frameworks to ensure that the final selections were aligned with the long-term goals of the project.

\textbf{Programming Language:} We selected \textbf{TypeScript} for our frontend development because it is built on JavaScript and has static typing capabilities, which enhance the code reliability, readability, and maintainability, especially for large-scale applications. Unlike JavaScript, TypeScript catches errors at compile time, making development more robust and reducing runtime bugs. It also offers better IDE support, including autocompletion and refactoring, which improves developer productivity.\cite{javascript-official, typescript}

\textbf{Frontend framework:} We chose \textbf{Next.js} as the main frontend framework for our project because it provides built-in support for server-side rendering (SSR) and static site generation (SSG), improving performance and initial load times. The App Router with folder-based routing simplified page organization and navigation setup, making development faster and more maintainable. Since Next.js is React-based, we continue to leverage React’s component model for building modular and reusable UI elements. Other frameworks, such as Angular or Vue, were considered but not selected due to steeper learning curves, heavier frameworks, and less alignment with our project’s React-focused architecture. This combination of features, performance optimizations, and developer productivity made Next.js the best choice for implementing the \textbf{Tourlingo} frontend.\cite{nextjs, angular-official, vue-official}

\vspace{2em}

\textbf{Styling:}
We chose \textbf{Tailwind CSS} as our styling foundation because its utility-first approach promised efficient styling while maintaining consistency across components, which was critical for scaling the project. DaisyUI, layered on top of Tailwind, further influenced our decision by providing prebuilt, themeable components that reduced design overhead and accelerated prototyping. At the same time, we anticipated the need for fine-grained control, so we kept the option of extending the setup with custom CSS for project-specific adjustments, such as hiding scrollbars and repositioning leaflet map controls.\cite{tailwindcss, daisyui, css-official}

\section{Frontend Implementation}

\subsection{Overview}
The frontend was delivered in various iterations. Each started with a clear problem, targeted a small set of outcomes, and ended with a working build shown to stakeholders. The implementation followed the Figma prototype, ensuring alignment between design and application. Reusable components were created and used to maintain consistency throughout the pages. We used Next.js and TypeScript, styled with Tailwind CSS. The state began local and was later centralised in a small Zustand store backed by localStorage. The frontend was responsible for navigating the application throughout and integrating the APIs.

\subsection{Iteration 1 - Clickable Prototype}
\textbf{Problem/Goal:} At project start, we required a navigable prototype that reflected the agreed user flows and visual language. The iteration goal was therefore to match the Figma design and allow end-to-end clicking through the core screens. 

\textbf{Implementation:} We built page flow across the Language, Map, Essentials, Recommendations, and Cultural Tips screens. To reduce risk backend dependency, we populated the views with placeholders and realistic mock data so that swapping in API responses later would be simple. The language selection persisted across refreshes via localStorage.

\textbf{Result:} A working, clickable prototype aligned to the Figma flows was delivered. Users could move between Language, Map, Essentials, Recommendations, and Cultural Tips. The location, tips and language are not lost evn afterreload and  persisted across refreshes via localStorage. Using realistic mock data made each screen demo-ready and let us validate layout. In the review, stakeholders confirmed the flows matched expectations and asked that Cultural Tips be broken into shorter, expandable sections.

\textbf{Known limitations:} No live data; no map directions; Cultural Tips were text-heavy; the map view did not persist between screens.

\subsection{Iteration 2 - From placeholders to data-driven pages}
\textbf{Problem/Goal:} The main goal here was to start showing real data from APIs and to simplify the experience by keeping everything within the Map view and making it responsive.  

\textbf{Implementation:} We connected the frontend to our backend, which uses OpenStreetMap and the Overpass API to fetch real points of interest. Essentials and Recommendations, which were originally separate pages, were reworked into slide-out panels that overlay the Map. This change meant users could explore places without losing their map view. Each item in the panels was linked to category pins on the map, so clicking a place in the list immediately highlighted the right marker.  

At the same time, we focused on reusable components. Shared UI elements were refined so they could be used consistently throughout the app. To make the experience feel smoother when data was loading, we added a loading animation at the end of this iteration. Finally, Cultural Tips, which had been one long block of text, were restructured into five clear sections (Etiquette, Must-know Phrases, Payment Methods, Transportation, and Emergency Numbers). We added expand/collapse controls to make the page easier to browse. We also made the app responsive, so it adapts to any screen size or device.  

\textbf{Result:} By the end of this iteration, users could stay on the Map page and see live Essentials and Recommendations with just one tap. The connection between list items and map pins made the interface more intuitive, while Cultural Tips became easier to read in smaller chunks. Reusable components reduced repeated code, and the loading animation gave users feedback while waiting for API calls. Quick checks on different devices showed the app was now responsive and worked well across screen sizes.  

\textbf{Known limitations:} The map view still reset after moving between screens, zoom controls could overlap the search bar on smaller devices, and directions had not yet been added.

\subsection{Iteration 3 - Smoother use, persistent state, and directions}
\textbf{Problem/Goal:} The goal of this iteration was to make the experience smoother and more practical by keeping state across reloads, speeding up how tips load, adding a simple guide for new users, and introducing walking, cycling, and driving routes.  

\textbf{Implementation:} We used the Zustand \cite{zustand-docs} store to manage map state in one place and added persistence with localStorage so that the location and tips remain after reloads. To cut waiting on Cultural Tips, we prefetch tips once the city and language are known, keep a recent copy in the store, and show that immediately when the user navigates to the page. The map now uses distinct markers for the user’s location, the selected destination, and each category in Essentials and Recommendations. To support new users, we added a short, guided tour using intro.js\cite{introjs-docs}. It runs only on first launch and walks through the main actions: choosing a language, exploring the map, and showing what each button on the navigation bar is responsible for. We also added directions for walking, cycling, and driving, with coloured routes, distance and time estimates, and step-by-step instructions in a side panel. Finally, we repositioned zoom controls and the guide help button to avoid overlap on small screens.  

\textbf{Result:} The app feels more responsive, holds its place between screens, and is easier to understand on first use. Cultural Tips appear quickly on return visits and remain visible after a refresh. Point-to-point directions were implemented, now the user can search for a location and get routing options for driving, cycling or walk.
